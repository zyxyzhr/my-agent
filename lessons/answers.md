# 理解题参考答案

> 先自己答，再对答案。答案看的是思路不是措辞。

## 第 1 课
1. **不记得。** 服务无状态，两次请求之间服务器不存任何东西；"记得"是靠每轮把历史重新发回去造出来的幻觉。
2. 常见还有 `role`（响应的 message 里恒为 assistant）；思考模型还会有 `reasoning_content`（思考过程）。字段存在但为 null（如某些响应的 `tool_calls: null`）说明该能力可用但这次没触发。
3. 两点：a) 输入端有固定开销——对话模板、角色标记等，不是"只有你的字"；b) 思考模型的 completion 里包含 reasoning_tokens（思考也计费），可见回答很短但 token 不少。
4. 涨的正是那条 system 消息的内容 + 角色标记（通常几个 token）。说明 system 不是免费的：每轮都发、每轮都计费。

## 第 2 课
1. **6 条**：1 system + 3 user + 2 assistant。关键：发送第 3 轮请求的时刻，模型还没回答 user3，所以 assistant 只有 2 条。公式：第 N 轮发 2N 条。
2. 每轮 +2 条消息 → 请求体变长 → prompt_tokens 每轮多付一遍（重复前缀有服务端缓存优惠，但上限仍在）。
3. 模型"失忆"：不知道自己说过什么，会接不上话、重复回答、甚至自相矛盾。
4. 在你 Python 进程里的一个列表（history）。进程一关就没了——这就是第 5 课持久化要解决的。

## 第 3 课
1. **没有。** 那一刻模型只是"生成了一段长得像函数调用的文本"（一张申请表）。真正执行发生在 ③，你的代码里。模型永远是文本生成器。
2. id 是对账编号：模型一轮可能申请多个工具，每条结果必须送回对应的那次申请，模型靠 tool_call_id 分辨"哪条结果对应哪次调用"。协议还要求一一对应：每个 tool_call 必须有一条对应 tool 结果消息，缺了 API 直接报错。
3. 模型只会输出文本（token 流），"结构化数据"只能用文本表示，所以是 JSON 字符串，代码端 json.loads 还原。实用后果：这个字符串可能是坏的（模型生成出错），解析要 try/except。
4. 两层：a) system prompt 里明确"必须用工具、严禁心算"；b) 代码端检查响应——没有 tool_calls 却直接给了答案，可以追加提示重试，严格场景拒收该回答。

## 第 4 课
1. 退出条件：响应没有 tool_calls（finish_reason=stop），或达到 max_steps。误判"停止信号"的后果：循环永不结束（工程上会先因取不到 tool_calls 抛异常——安全阀和检查正是为此）。
2. API 协议层直接拒收（400）：每个 role=tool 消息必须紧跟在含对应 tool_calls 的 assistant 消息之后。注意是**请求到不了模型**，不是"模型会懵"。
3. 防模型反复调用工具形成死循环。真实场景：工具持续报错、模型持续重试；或模型对"再查一次时间"这类请求无限循环调用。
4. 17/0 常见走"正确解释"（除数不能为 0，未定义）；17+*8 常见走"自我探索"——一轮并行算出 17+8 和 17*8 两种解释都给你，甚至不触发任何报错。跑一下验证你的猜测。

## 第 5 课
1. usage 是服务端 tokenizer 的官方计数（也是计费依据）；自己按字数估不准——不同语言/符号的 token 切分率不同，还有模板开销。
2. API 协议层直接拒收请求（400），请求根本到不了模型——是"门口"拦的，不是"屋里的人"。
3. 解决：你进程这边的记忆活过进程死亡（重启/崩溃不丢）。没解决：模型服务端依然无状态，每轮你仍要把全部历史发过去——磁盘存的是"你的记忆"，不是"模型的记忆"。
4. 摘要记忆：让 LLM（同一个或另一个）把旧对话总结成一段话；以一条 user 消息（"[以下是之前对话的摘要：…]"）或并入 system 的形式放进 messages；代价 = 细节丢失 + 摘要本身一次额外的 LLM 调用（时间+钱）。

## 第 6 课
1. 该重试：429、5xx、网络错误/超时。不该：其他 4xx（尤其 401）。因为重试的本质是赌"状态会变"——429/5xx/网络是临时状态，会恢复；401 是凭证错了，同样的请求一万次判定都一样。
2. 固定间隔 = 同步塌方：1000 个客户端同时 429、1 秒后 1000 个请求同时砸回来，服务器再倒、再 429、无限循环。指数退避让每个人的等待时长按 1/2/4 增长，重试时刻自然散开（去同步），流量随时间衰减；真实系统再加随机抖动。
3. HTTP 响应体是无边界的字节流，没有天然"一条消息到哪儿结束"的标记，需要文本约定分帧：`data: ` 行 = 一个事件的数据（SSE 还有 event:/id: 等其他行，前缀用来区分）；`[DONE]` = 显式终止信号（没有它只能靠连接关闭来猜）。
4. reasoning_content 先。含义：a) 思考模型上，拿到第一个正字的时间 = 全程思考时间，"秒出首字"红利被吃掉；b) 但等待不再是干等——reasoning 流可以实时显示（"正在思考…"动画），等待变成了信息。
5. **没有本质区别。** 框架 = 循环 + 工具注册 + 上下文管理（你手写过的三件套）更完整、更通用的版本，外加预置工具/多模型适配等"肉"。从零写一遍的价值：读得懂框架源码、抽风时知道 debug 哪层、任何环境 30 分钟手搓最小 Agent。
