# 第 5 课：记忆与上下文管理

> 预计 60 分钟｜动手文件：`agent.py`（在第 4 课基础上追加）+ `test_lesson5.py`｜前置：第 4 课

## 一、目标
让 Agent 的上下文"可观察、可截断、可持久化"。完成后你能讲清楚上下文是怎么涨的、怎么管。

## 二、理论（10 分钟读完）
**上下文窗口 = Agent 的"内存"，它是有限的。** 每聊一轮 prompt_tokens 涨一截，不管它 = 总有一天请求被拒。

三件管理工具：

1. **观察**：读响应里的 `usage.prompt_tokens`——服务端 tokenizer 的官方计数，
   比你自己数文本可靠（中文约 1~2 token/字、英文约 4 字符/token、还有模板开销）。这也是计费依据。
2. **截断**：滑动窗口保留最近 N 条。**坑：切点不能留下孤儿 role=tool 消息**（它对应的 tool_calls 申请书被切掉了）→ API 400。
   正确姿势：先算切点下标，若切点处的消息是 tool 就切点 +1，直到不是。
3. **持久化**：历史写磁盘、重启恢复——"记忆"第一次活过进程。
   注意：你持久化的是"你这边"的记忆。模型服务端依然无状态，每轮你仍要把全部历史发过去——
   **记忆永远是客户端的构造物，所有 Agent 框架（包括 LangChain）都是这个架构。**

进阶预告（不用实现）：对话 500 轮快撑爆窗口时，截断之外的招是**摘要记忆**——
让 LLM 把旧对话总结成一段话，以一条 user 消息（或并入 system）放进 messages。
代价：细节丢失 + 摘要本身要一次额外的 LLM 调用。

## 五、理解题
1. 为什么信 usage.prompt_tokens 而不自己估 `len(文本)`？
2. 截断切出孤儿 tool 消息会怎样？（谁报错——API 层还是模型？）
3. 磁盘持久化解决了什么问题？又**没有**解决什么？
4. 进阶：500 轮快撑爆窗口，除了截断还有什么招？摘要谁来做、以什么形式进 messages、代价是什么？

## 六、常见坑
- "算了新值忘了返回"：算出 trimmed 却 return 了原列表——本测试会抓住它
- 截断用切片重构容易写错（列表越切越长）；切点下标法最稳
- `exists()` 只处理"文件不存在"，不处理"文件损坏"（JSONDecodeError）
- **测试为准**："我觉得修好了" ≠ "测试是绿的"。设计测试要让它"函数空转时必红"
